# Contributing

Start with the project plan and open issues. The first release is intentionally local and small. Propose substantial scope or stack changes in an issue before implementation.

For code, use a focused branch and pull request describing the user-visible behavior, issue addressed, validation, and remaining limitations. Development commands will be added with the application scaffold. Do not imply tests ran when the relevant application does not exist yet.

For catalog contributions, read DATA_POLICY.md. Submit original observations or permissioned material with sources and dates. Do not paste guidebook pages or copy route descriptions from other sites. Keep precise sensitive locations and permission correspondence out of public issues. Report access problems without amplifying restricted information.

For bugs and features, explain the scenario, expected behavior, and acceptance criteria. Be respectful of people and climbing areas. Pseudonymous participation is welcome. Maintainers may remove spam, harassment, private personal information, or unauthorized source content.

Do not report security vulnerabilities or credentials in a public issue. Until a private reporting channel is configured, contact the repository owner privately through an already established channel. Configuring private vulnerability reporting is part of the deployment backlog.
